## 4. テスト設計と検証項目

各課題のテストシナリオと期待結果、およびエビデンスとして保存するスクリーンショットのタイミングを定義します。

### ■ 課題1 (CN-057-9-1) テストケース
一括登録（POST）のみの検証。
1. **初期状態作成**:
   - テスト用の「受注管理」レコードを1件新規作成し、サブテーブルに2行（商品データ）を追加する。
2. **操作**:
   - 作成した「受注管理」レコードの「詳細画面」へ遷移。
   - 「テーブル展開#1」ボタンをクリック。
3. **検証項目**:
   - 登録完了のアラートダイアログ（`受注明細アプリへ 2 件の明細展開登録が完了しました！`）が表示されること。
   - 受注明細アプリ側に、受注管理から展開されたデータ（受注番号、受注日、顧客コード、商品コード_0、カテゴリ、商品名、単価、数量、小計）を持つ2件のレコードが正しく登録されていること。
   - 元の受注管理レコードのサブテーブル内の「受注明細番号」フィールドが **空のまま** であること。
4. **エビデンス画像保存**:
   - `e2e/evidence/CN-057-9-1/01_before_click.png` (ボタン押下前)
   - `e2e/evidence/CN-057-9-1/02_alert.png` (完了アラート表示時)
   - `e2e/evidence/CN-057-9-1/03_after_click.png` (親レコードの状態)
   - `e2e/evidence/CN-057-9-1/04_detail_records.png` (登録された受注明細一覧画面)

## 8. 開発時のトラブルシューティング (トラブルと対策の記録)

本テスト環境の構築およびテストコードの実装中に発生した問題と、それに対する技術的なアプローチ・解決策の記録です。

### 8.1. APIリクエスト時の 400 Bad Request（エラーコード: `CB_IL02`）
- **現象**:
  `getRecordDetails`（GET）および `cleanupChildRecords`（GET）をPlaywrightの `request.get` の `params` オプション経由で実行した際、kintone 側から「不正なリクエスト（CB_IL02）」として 400 エラーが返されました。
- **原因**:
  共通ヘッダー（`headers`）に定義されていた `Content-Type: application/json` が GET リクエスト時にも付与されていたため、kintone のWebサーバーが「JSONデータを伴うGETリクエストであるが、ボディが空、またはパースできない」と判断し、パースエラー（CB_IL02）となっていました。
- **対策**:
  GETリクエストを投げる際は、`Content-Type` ヘッダーを送信せず、認証ヘッダー `X-Cybozu-Authorization` のみを送信するように設定を切り分けました。また、パラメータはPlaywrightのシリアライズに依存せず、URLに直接クエリ文字列（`?app=X&id=Y`）として組み立てる形式に変更し、100% 安定した通信を確立しました。

### 8.2. ダイアログ表示状態でのスクリーンショット撮影によるタイムアウト
- **現象**:
  「テーブル展開」ボタンクリック時に表示されるアラートダイアログ（`window.alert`）が開いた状態でスクリーンショット（`02_alert.png`）を撮影しようとしたところ、Playwright の `page.screenshot` が15秒間でタイムアウトしました。
- **原因**:
  ネイティブアラートダイアログが表示されている間、ブラウザの描画およびJavaScriptスレッドが完全にブロッキングされます。この状態でPlaywrightが `fullPage: true`（ページ全体の高さをスクロール描画する）で撮影を行おうとすると、完了せずデッドロックが発生するためタイムアウトになっていました。
- **対策**:
  自動テスト（ヘッドレスモード）においてはブラウザネイティブのダイアログは描画されない（グレーアウトした背景しか写らない）ため、ダイアログ表示中のスクリーンショット撮影自体を廃止しました。ダイアログが発火した際は即座に承認（`dialog.accept()`）し、アラートメッセージの検証はテキストアサーション（`expect(alertMessage).toContain(...)`）のみで行う設計に最適化しました。

### 8.3. kintoneのフィールド型制約による登録・比較エラー
- **現象**:
  - 親レコード新規作成の API (POST) 実行時に `RECORD_ID型のフィールドに値を設定することはできません` とエラーが出力されました。
  - 子明細アプリへのクエリ（GET）実行時に `不正なリクエストです` とエラーが出力されました。
- **原因**:
  - 親アプリの「受注管理No」のフィールド型は `RECORD_ID`（自動採番）であり、API経由で値を任意設定することができませんでした。
  - 子アプリの「受注番号」（ラベル: 受注管理No）のフィールド型は `DECIMAL`（数値型）であり、テスト用の識別文字列（例: `"E2E-CASE1"`）を値として設定したり、文字列比較クエリを投げたりすることが型不整合で許可されませんでした。
- **対策**:
  - レコード作成時の `RECORD_ID` フィールド（`受注管理No`）はAPI送信データから除外しました。
  - テストのクリーンアップや子レコードの特定は、文字列ではなく、自動採番された親レコードID（整数値）をそのまま `受注番号` のクエリ比較や登録パラメータとして使用する手順に変更し、数値比較（`query: 受注番号 = parentRecordId`）を行うことで型整合性を保つ設計に修正しました。
