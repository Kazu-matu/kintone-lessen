# E2Eテスト計画書 (Playwright)

## 1. 背景と目的

本計画書は、kintoneアプリ（「受注管理」アプリおよび「受注明細」アプリ）に適用したサブテーブルのデータ展開用カスタマイズJavaScript（課題1〜3）が、設計および機能要件通りに動作するかをPlaywrightを用いて自動検証し、実行結果のエビデンス画像（スクリーンショット）を収集するための手順と設計を定義します。

---

検証対象となる仕様書およびカスタマイズコードは以下の通りです。

| 課題ID | 仕様書ドキュメント | 対象JavaScriptコード | 主な機能 |
| :--- | :--- | :--- | :--- |
| **課題1** | [CN-057-9-1.md](file:///z:/kintone/docs/CN-057-9-1.md) | [table_expand_1.js](file:///z:/kintone/src/課題/table_expand_1.js) | サブテーブル行を明細アプリに新規一括登録（POST） |
| **課題2** | [CN-058-9-2.md](file:///z:/kintone/docs/CN-058-9-2.md) | [table_expand_2.js](file:///z:/kintone/src/課題/table_expand_2.js) | 新規一括登録（POST）後、発行された明細IDを親サブテーブルへ書き戻し（PUT） |

## 3. テスト環境

- **言語・フレームワーク**: JavaScript / Node.js
- **テストライブラリ**: Playwright (`@playwright/test`)
- **設定値管理**: `.env` ファイルによる環境変数管理
- **必要な接続・認証情報**:
  - `KINTONE_BASE_URL`: kintone環境のベースURL (例: `https://xxxx.cybozu.com`)
  - `KINTONE_USER`: ログインユーザー名
  - `KINTONE_PASSWORD`: ログインパスワード
  - `APP_ID_PARENT`: 受注管理（親）アプリID
  - `APP_ID_CHILD`: 受注明細（子）アプリID

---

## 4. テスト設計と検証項目

各課題のテストシナリオと期待結果、およびエビデンスとして保存するスクリーンショットのタイミングを定義します。

### ■ 課題1 (CN-057-9-1) テストケース
一括登録（POST）のみの検証。
1. **初期状態作成**:
   - テスト用の「受注管理」レコードを1件新規作成し、サブテーブルに2行（商品データ）を追加する。
2. **操作**:
   - 作成した「受注管理」レコードの「詳細画面」へ遷移。
   - 「テーブル展開#1」ボタンをクリック。
3. **検証項目**:
   - 登録完了のアラートダイアログ（`受注明細アプリへ 2 件の明細展開登録が完了しました！`）が表示されること。
   - 受注明細アプリ側に、受注管理から展開されたデータ（受注番号、受注日、顧客コード、商品コード_0、カテゴリ、商品名、単価、数量、小計）を持つ2件のレコードが正しく登録されていること。
   - 元の受注管理レコードのサブテーブル内の「受注明細番号」フィールドが **空のまま** であること。
4. **エビデンス画像保存**:
   - `e2e/evidence/CN-057-9-1/01_before_click.png` (ボタン押下前)
   - `e2e/evidence/CN-057-9-1/02_alert.png` (完了アラート表示時)
   - `e2e/evidence/CN-057-9-1/03_after_click.png` (親レコードの状態)
   - `e2e/evidence/CN-057-9-1/04_detail_records.png` (登録された受注明細一覧画面)

---

### ■ 課題2 (CN-058-9-2) テストケース
一括登録（POST）およびID書き戻し（PUT）の検証。
1. **初期状態作成**:
   - テスト用の「受注管理」レコードを1件新規作成し、サブテーブルに2行（商品データ）を追加する。
2. **操作**:
   - 作成した「受注管理」レコードの「詳細画面」へ遷移。
   - 「テーブル展開#2」ボタンをクリック。
3. **検証項目**:
   - 登録完了のアラートダイアログ（`受注明細の登録および受注明細番号の書き戻しが完了しました。`）が表示されること。
   - アラート承諾後に画面がリロードされ、親レコードのサブテーブル内の「受注明細番号」フィールドに、新規作成された明細レコードのIDがそれぞれ自動で入力（書き戻し）されていること。
   - 受注明細アプリ側に該当IDのレコードが存在すること。
4. **エビデンス画像保存**:
   - `e2e/evidence/CN-058-9-2/01_before_click.png`
   - `e2e/evidence/CN-058-9-2/02_alert.png`
   - `e2e/evidence/CN-058-9-2/03_after_click.png` (書き戻されたサブテーブルの状態)
   - `e2e/evidence/CN-058-9-2/04_detail_records.png`

---

### ■ 課題3 (CN-059-9-3) テストケース
新規・既存の自動判別（POST / PUT分岐）と並行処理の検証。
1. **初期状態作成**:
   - サブテーブルに3行のデータを持つ「受注管理」レコードを作成する。
   - そのうち、1行目と2行目には事前に実在する「受注明細番号」を設定しておく（既存レコード）。3行目は「受注明細番号」を空にしておく（新規レコード）。
2. **操作**:
   - レコードの「詳細画面」へ遷移し、「テーブル展開#3」ボタンをクリック。
3. **検証項目**:
   - 完了のアラートダイアログ（`テーブル展開（新規登録＆更新）が正常に完了しました。`）が表示されること。
   - 画面がリロードされた後、新規だった3行目にだけ新しい「受注明細番号」が書き戻されていること。
   - 既存だった1行目と2行目について、受注明細アプリ側の対応レコードが更新されていること（例: 数量や小計などの値が更新されていること）。
4. **エビデンス画像保存**:
   - `e2e/evidence/CN-059-9-3/01_before_click.png`
   - `e2e/evidence/CN-059-9-3/02_alert.png`
   - `e2e/evidence/CN-059-9-3/03_after_click.png`
   - `e2e/evidence/CN-059-9-3/04_detail_records.png`

## 6. テスト実行方法

### 6.1. 事前準備
1. Node.jsのインストール。
2. 依存パッケージのインストール:
   ```bash
   npm install
   ```
3. 環境変数ファイル `.env` の作成。
4. kintoneアプリ側に検証対象のカスタマイズJavaScriptが正しくアップロードされていること。

### 6.2. テストの実行
```bash
npx playwright test
```
テスト結果および収集されたスクリーンショットが `e2e/evidence` フォルダ内に保存されます。
