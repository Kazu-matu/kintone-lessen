## 1. 概要
本ドキュメントは、kintone上の「受注管理」アプリから「受注明細」アプリへのテーブル展開処理（課題1、課題2、課題3）を検証するPlaywrightを用いた自動E2Eテストスクリプト `z:\kintone\e2e\table_expand.spec.js` の動作仕様書である。

本テストは、画面上のボタン操作と、kintone REST APIを組み合わせることで、データの自動セットアップ・クリーンアップを完全に自動化し、テスト実行後のゴミデータが残らない堅牢な設計となっている。

---

## 2. システム構成と動作環境

### 2.1. 接続先情報
- **ベースURL**: `.env` 内の `KINTONE_BASE_URL` (例: `https://kazu-lab.cybozu.com`)
- **ログインユーザー名**: `.env` 内 of `KINTONE_USER`
- **ログインパスワード**: `.env` 内 of `KINTONE_PASSWORD`
- **親アプリ (受注管理)**: アプリID: `22` (環境変数 `APP_ID_PARENT`)
- **子アプリ (受注明細)**: アプリID: `24` (環境変数 `APP_ID_CHILD`)

### 2.2. 主要な依存ライブラリ
- `@playwright/test`: E2Eテストの実行フレームワーク。
- `dotenv`: 環境変数の管理。
- `fs` / `path`: エビデンス画像の自動保存先ディレクトリ制御。

## 3. テストスクリプトの構造と共通処理

`e2e/table_expand.spec.js` で提供されている主要なヘルパー関数の動作仕様を示す。

### 3.1. 共通ヘルパー関数

#### 1) `takeScreenshot(page, caseName, imageName)`
- **処理概要**: 指定されたフォルダ配下に、画面のスクリーンショットをPNG形式で保存する。
- **保存先**: `e2e/evidence/{caseName}/{imageName}`
- **引数**:
  - `page`: PlaywrightのPageオブジェクト
  - `caseName`: フォルダ名（例: `CN-057-9-1`）
  - `imageName`: 画像ファイル名（例: `01_before_click.png`）

#### 2) `loginKintone(page)`
- **処理概要**: `/login` 画面から環境変数のユーザー・パスワードを入力してログインする。ログイン後、サービス一覧（`/`）から明示的に kintone ポータル（`/k/#/portal`）へナビゲートして画面描画を待つ。

#### 3) `createTestParentRecord(request, recordNo, tableRows)`
- **処理概要**: テスト用の受注管理レコード（親レコード）を1件、kintone REST API (POST) を用いて作成する。
- **仕様**:
  - `RECORD_ID`（自動採番）の `受注管理No` フィールドはAPI送信データから除外する。
  - `発注者`（文字列型）フィールドに、テストの識別子である `recordNo`（例: `E2E-CASE1-1785...`）を設定する。
  - サブテーブル（受注明細Table）の各行に対し、`受注明細番号` は `detailId` が渡された場合のみセットし、新規行の場合は値自体をAPIパラメータから除外する（数値型 `DECIMAL` に対する空文字エラーを防ぐため）。

#### 4) `getRecordDetails(request, appId, recordId)`
- **処理概要**: 指定したアプリおよびレコードIDの詳細データをAPI経由で取得する。
- **仕様**:
  - GETリクエストの仕様に準じ、`Content-Type` ヘッダーを取り除き、クエリパラメータを手動で組み立ててリクエストする（例: `/k/v1/record.json?app=${appId}&id=${recordId}`）。

#### 5) `cleanupChildRecords(request, parentRecordId)`
- **処理概要**: 数値型の `受注番号` を持つ受注明細（子レコード）のうち、親レコードID（`parentRecordId`）と一致する明細をAPI経由で全削除（DELETE）する。
- **仕様**:
  - クエリ文字列を手動で組み立ててGETリクエストを投げ（`受注番号 = ${parentRecordId}`）、取得できた子レコードのID配列をDELETE APIに引き渡す。

#### 6) `cleanupParentRecord(request, parentRecordId)`
- **処理概要**: 作成した親レコードをAPI経由で削除（DELETE）する。

## 4. テストケース（テストシナリオ）仕様

### 4.1. 課題1 (CN-057-9-1): 新規一括登録（POSTのみ）の検証
- **目的**: 親レコード内のサブテーブルをすべて展開し、受注明細アプリへ新規に一括登録できることを検証する。
- **テスト手順**:
  1. API経由で、受注明細Tableが2行（受注明細番号は空）の親レコードを作成する。
  2. 対象の親レコード詳細画面（`show#record=XX`）へ遷移する。
  3. 画面上にボタン「テーブル展開#1」（`#btn_table_expand_1`）が存在することを確認し、クリック前スクリーンショットを撮影 (`01_before_click.png`)。
  4. ボタンをクリックし、ダイアログメッセージ `受注明細の一括登録が完了しました。` を検知・承認する。
  5. 画面が自動リロードされた後、親レコード詳細画面のスクリーンショットを撮影 (`03_after_click.png`)。
  6. **アサーション**:
     - 親レコードのサブテーブルの「受注明細番号」がすべて **空のまま** であることを確認する（課題1の仕様）。
     - 受注明細アプリを直接APIで参照し、親レコードIDと紐づく2件の子レコード（商品コード: `BBB01`, `CCC01`）が正しく登録されていることを検証する。
  7. 子アプリのレコード一覧画面へ遷移し、エビデンスを撮影 (`04_detail_records.png`)。

---

### 4.2. 課題2 (CN-058-9-2): 一括登録と採番ID書き戻し（POST & PUT）の検証
- **目的**: 受注明細アプリへ新規登録し、かつ自動採番された明細ID（レコード番号）を、親レコードのサブテーブルに自動的に書き戻す（PUT更新）動作を検証する。
- **テスト手順**:
  1. API経由で、受注明細Tableが2行（受注明細番号は空）の親レコードを作成する。
  2. 対象 of 親レコード詳細画面へ遷移する。
  3. ボタン「テーブル展開#2」（`#btn_table_expand_2`）を確認し、クリック前エビデンスを撮影 (`01_before_click.png`)。
  4. ボタンをクリックし、ダイアログメッセージ `受注明細の登録および受注明細番号の書き戻しが完了しました。` を検知・承認する。
  5. 画面リロード後、親詳細画面のエビデンスを撮影 (`03_after_click.png`)。
  6. **アサーション**:
     - 親レコードのサブテーブル内「受注明細番号」に、**空ではない数値（明細のレコード番号）が書き戻されていること** を確認する。
     - 書き戻された各明細番号（ID）で受注明細アプリを直接APIで参照し、それぞれ対応する商品情報（`BBB01`, `CCC01`）が登録されていることを検証する。
  7. 子アプリのレコード一覧画面へ遷移し、エビデンスを撮影 (`04_detail_records.png`)。

---

### 4.3. 課題3 (CN-059-9-3): 新規・既存の自動判別と更新（POST/PUT並行処理）の検証
- **目的**: 親レコードのサブテーブルにすでに存在する明細ID（既存明細）がある場合は「更新（PUT）」し、明細IDが無い行は「新規登録（POST）」する並行処理を検証する。
- **テスト手順**:
  1. まず親レコードを一度作成する。
  2. その親レコードIDを親キーとして持つダミー明細（子）を2件APIで直接作成する（既存明細の仮作成）。
  3. 親レコードのサブテーブルを更新し、1行目と2行目に作成した明細IDをセットし、かつ数量の値を変更する（10 ➡ 20, 5 ➡ 15）。また、3行目として受注明細番号が「空」の新規行を追加する。
  4. 対象の親レコード詳細画面へ遷移する。
  5. ボタン「テーブル展開#3」（`#btn_table_expand_3`）を確認し、クリック前エビデンスを撮影 (`01_before_click.png`)。
  6. ボタンをクリックし、ダイアログメッセージ `テーブル展開（新規登録＆更新）が正常に完了しました。` を検知・承認する。
  7. 画面リロード後、親詳細画面のエビデンスを撮影 (`03_after_click.png`)。
  8. **アサーション**:
     - サブテーブルの1行目・2行目の「受注明細番号」には、**元々の既存ID** が変わらず維持されていることを確認する。
     - 3行目（新規行）の「受注明細番号」に、**新しく採番された明細ID** が自動で書き戻されていることを検証する。
     - APIで既存明細（1行目・2行目）のデータを取得し、数量がそれぞれ `20`, `15` に更新されていることを確認する。
  9. 子アプリのレコード一覧画面へ遷移し、エビデンスを撮影 (`04_detail_records.png`)。

## 5. 実装上の考慮点（トラブルシューティング対策）

本テストスクリプトには、kintoneおよびPlaywright固有の制限を回避するための以下の設計が組み込まれている。

### 5.1. GETリクエストにおける Content-Type ヘッダーの排除
- kintoneの REST API に `GET` メソッドでアクセスする際、共通の `headers` に `Content-Type: application/json` が付与されていると、ボディが空でもJSONパースエラー (`CB_IL02`) が発生する。
- これを避けるため、`getRecordDetails` および `cleanupChildRecords` 内では `Content-Type` を排除し、認証ヘッダーのみでクエリパラメータを直接URL文字列に結合して送信する。

### 5.2. ダイアログ表示中のスクリーンショット撮影の禁止
- ブラウザのアラートダイアログ（`window.alert`）が開いている間、ブラウザスレッドが完全にブロックされる。
- Playwrightの `page.screenshot`（特に `fullPage: true`）を実行すると描画スレッドとの競合によりデッドロックが発生し、15秒のタイムアウトエラーを引き起こす。
- 本テストでは、アラートダイアログ表示中の撮影（`02_alert.png`）を完全に排除し、`dialog.accept()` によるクローズと、メッセージ内容の文字列検証（`expect(alertMessage).toContain`）のみで評価する。

### 5.3. DECIMAL（数値）型クエリの整合性
- 受注明細アプリ側の `受注番号` フィールドは `DECIMAL`（数値型）として定義されている。
- API経由でのクエリ発行時に `query: 受注番号 = "E2E-CASE..."` のように文字列で比較すると型不整合（`CB_IL02`）エラーが発生する。
- テスト内では、動的に採番された親のレコードID（数値）をそのままクエリ比較に使用し、`query: 受注番号 = ${parentRecordId}` とすることで型安全性を保証している。
